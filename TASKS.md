### Cellular data hardening / optimization

Discovered while validating `wata-metricsd` cellular field reads (2026-04-13). The modem hardware and SIM are fine — Swiss LTE coverage is excellent (Swisscom/Salt/Sunrise all `available, roaming, not-forbidden` on a network scan, RSSI -77 dBm on UMTS-900) — but the modem takes minutes-to-never to attach because of how it's configured.

**Root cause**: the modem's default `system-selection-preference` has acquisition order `cdma-1x, cdma-1xevdo, gsm, umts, lte, td-scdma` — **LTE is last**. The modem finds UMTS-900 first (Salt, MCC=228 MNC=03), gets `WCDMA Status: limited` because the SIM (Singtel, MCC=525 MNC=1) isn't allowed PS attach there, and parks on it without ever trying LTE. The CLAUDE.md hardware spec says "4G LTE data-only" but the actual config doesn't enforce that.

- [x] **Force LTE-only mode at cellular bringup** — `cell-data wake` now calls `ensure_lte_prefs` which idempotently applies `lte,automatic` if not already set. Acquisition order becomes `lte, umts, gsm, …` so LTE is tried first.
- [x] **Persist mode preference across modem resets** — verified: the QMI NAS preference is stored in modem NV and survives both `dms-set-operating-mode=reset` and full device reboots. `ensure_lte_prefs` is therefore a no-op after the first application. No oneshot service needed.
- [x] **Robust modem state-machine in `cell-data.sh`** — rewritten with a bounded 2-minute budget: `set_online` handles `online`/`low-power`/`offline`/`shutting-down`/`resetting` and escalates to `dms reset` + 10 s settle once on timeout. `do_wake` returns exit 1 for unreachable-online and exit 2 for PS-attach timeout, so callers (and `smoke-cellular`) can distinguish firmware deadlock from coverage/roaming problems.
- [x] **Roaming detection and logging** — `log_serving` records `plmn`, `rat`, `roaming` bool (MCC/MNC mismatch vs `nas-get-home-network`), home PLMN, and QMI's own roaming status to `/var/log/cellular.log` on every successful attach.
- [x] **`just smoke-cellular` end-to-end recipe** — runs `cell-data wake && up && ping -I ppp0 8.8.8.8 && down` against the live device. `just push-cell-data` scp's the current script in-place for quick iteration without a rootfs rebuild.
- [x] **Document the cellular bringup chain** — `docs/modem_data.md` now has a "Bringup chain (2026-04-13)" section with the sequence, expected prefs, recovery table, and smoke-test pointer.
- [x] **Approved roaming partners list — generated from authoritative source** — the runtime file `/etc/cellular/roaming-partners` is now auto-generated by `tools/gen-roaming-partners.py` (wired as `just gen-roaming-partners`), joining `eskimo_roaming.md` (manually extracted from https://www.eskimo.travel/en/network-coverage, 2026-04-13) against `tools/data/mcc-mnc-list.json` (vendored pbakondy/mcc-mnc-list, ~3000 operators). - [ ] **⏭️ NEXT: DIAG NAS log subscription** — every session spent on the attach failure has been blind guessing because we have no visibility into *why* a given attach attempt didn't complete. The Qualcomm DIAG framework exposes exactly this: subscribe to NAS EMM/ESM log packet IDs and you get the real EMM-cause and ESM-cause codes (e.g. #14 "EPS services not allowed in this PLMN", #15 "no suitable cells in tracking area", #13 "roaming not allowed in this TAI", #8 "operator determined barring", #19 "ESM failure", etc). Without these codes we can't tell whether the modem is refusing Sunrise cells (RF / cell-reselection bias / tracking-area reject), the network is rejecting us (HSS / auth / roaming-agreement), or a T3402/T3412 backoff timer is keeping the modem silent after a prior failed attempt. **State we start from**: `/dev/diag` is already opened and readable on this kernel (see `docs/modem_data.md` + the `modem_decompiled_src/pass7_diag*.c` notes); `tools/diag-efs-write.c` shows working DIAG packet framing against our modem; `tools/diag-apdu.c` shows a round-trip diag request/response; DIAG CNTL feature-mask handshake was verified in a prior session but cmd-registration was blocked on modem port state (see `memory/project_diag_state.md`). **Work needed**: (1) write a small `cell-diag` daemon (or extend `cell-data`) that (a) opens `/dev/diag` with the right ioctl to reach the modem processor, (b) sends DIAG CNTL to subscribe to NAS log packet IDs — at minimum the EMM state, ESM state, and RRC connection-setup log codes (exact codes are in QCAT's log-mask reference; also findable in the `modem_decompiled_src/` pass-7 dumps), (c) parses each incoming log packet just enough to extract `{timestamp, packet_id, emm_state, esm_state, cause}` and log one line per event to `/var/log/cellular-diag.log`; (2) cross-check the output against a known-working attach on the test iPhone location (expect a clean EMM-REGISTERED + ESM PDN_CONNECT with no reject codes); (3) use it to capture a failing BQ268 attach end-to-end and finally see the reject cause. **Why now**: this unblocks the "Live LTE attach still failing" item above — right now we're stuck guessing between RF/reselection, HSS rejection, NAS backoff, and MCFG policy. **Pointers**: `docs/planning/cellular-attach-resume.md` has prior sessions' findings; `memory/project_diag_state.md` has the DIAG CNTL state summary; `~/libqmi` has no DIAG helpers (DIAG is separate from QMI — it's the raw diagnostic framing over `/dev/diag`, not over msm_ipc_router). Once this task is done, **close task #8 next** (clean boot = clean drop_count baseline for DIAG captures), then resume the "Live LTE attach still failing" investigation with real cause codes.
